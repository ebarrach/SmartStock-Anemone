============================================================
1. OBJECTIF DU PROJET
============================================================

SmartStock est un projet universitaire de gestion intelligente
d'un espace de stockage médical. L'application illustre deux cas :

DÉMO 01 — GESTION INTELLIGENTE DU STOCK
Deborah retire une boîte de compresses. Deux événements distincts,
poids et Data Matrix, doivent être traités avant confirmation.
Le moteur fait évoluer stock(compresse,40) vers 39 puis 38.

DÉMO 02 — RÉGULATION INTELLIGENTE DE TEMPÉRATURE
L'utilisateur simule une température. Anemone applique une table
d'équations pour décider une puissance de ventilation. Deux
ventilateurs graphiques représentent la puissance reçue.

Les seuils de température sont des SEUILS DE DÉMONSTRATION,
pas des recommandations médicales ou pharmaceutiques.
Aucun pilote de capteur, scanner ou ventilateur physique n'est inclus.

Exigence principale : Anemone reste le vrai moteur métier du mode
ANEMONE. Les règles stock et ventilation ne sont pas remplacées
par des conditions Java ou JavaScript dans ce chemin.

4. DÉMARRAGE DU PROJET
============================================================

DANS INTELLIJ
1. Ouvrir ce projet et sélectionner le SDK Java 8 installé.
2. Vérifier la bibliothèque Anemone déclarée dans
   .idea/libraries/Anemone.xml si le JAR a changé de place.
3. Choisir SmartStock — Anemone réel.
4. IntelliJ compile notre module et lance smartstock.Main avec son
   classpath (classes SmartStock + vrai JAR) et la racine comme working dir.

Le JAR n'est pas "chargé par une API HTTP". Le classloader normal
de la JVM résout les classes importées depuis le classpath.
Leur origine effective est vérifiable dans le diagnostic CodeSource.

ALTERNATIVE POWERSHELL

powershell -NoProfile -ExecutionPolicy Bypass -File .\bridge\start.ps1

Autre port et/ou JAR :
powershell -NoProfile -ExecutionPolicy Bypass -File .\bridge\start.ps1 -Port 8092 -AnemoneJar "D:\chemin\Anemone.jar"

Ordre de choix du JAR par les scripts : paramètre -AnemoneJar,
puis variable ANEMONE_JAR de la session, puis bridge.properties.
start.ps1 appelle build.ps1, qui utilise javac -cp avec le JAR,
puis lance java -cp avec les classes compilées ET le JAR externe.
L'option Bypass concerne seulement ce processus PowerShell.
Aucune modification des politiques système n'est nécessaire.

JVM -> propriété headless -> racine/port -> deux EventHub ->

DATA MATRIX
Même chemin avec data-command="datamatrix", la route

POST /api/run -> prepare analyse l'agent s'il faut en créer un.
Une continuation bloquée existante est conservée.

chaque appel. RUN s'arrête sur false, agent vide ou erreur.

PAS À PAS
POST /api/step -> prepare puis un seul advance/run_one.
Dans la GUI historique, le bouton de pas s'appelle Next.
Dans le Visualizer, il s'appelle PAS À PAS.

Les identifiants HTTP évitent un double traitement récent d'une
même commande. Deux clics distincts sont deux commandes distinctes.


============================================================
6. DÉMO STOCK — QUI FAIT QUOI ?
============================================================

stock(compresse,40) : état métier, 40 boîtes.
poids_change(compresse) : événement poids.
datamatrix_detecte(compresse) : événement du scan Data Matrix.
retrait_confirme(compresse) : confirmation publiée par l'agent.

Les définitions sont dans connected/definitions.anemone :
Stock contient 0..40 ; pred est défini de pred(1)=0 à pred(40)=39.
La définition d'un ensemble ou d'une équation n'est pas un terme
du Current store : les deux types de données sont séparés dans ABBlackboard.

Le frontend ne calcule jamais la nouvelle quantité en mode réel.
Le Bridge ne décrémente pas. Son extraction parcourt les vrais
AB_SI_COMPOSED de foncteur stock, vérifie l'argument compresse et
lit le second argument. Il retourne null si le stock est absent
pendant la transition ou s'il est incohérent.

Anemone consomme les événements, confirme, sélectionne q=40 via
sum/get, consomme stock 40 et simplifie pred(40) en 39 avant tell.
Une autre exécution sur le même store peut sélectionner 39 et
publier 38. Les confirmations s'accumulent par multiplicité.

La séquence est NON atomique : le poids seul peut être consommé
avant blocage sur le Data Matrix absent. Le Bridge conserve l'AST.
L'ajout du Data Matrix puis RUN reprend cette même continuation.
Il n'y a pas d'attente automatique infinie après un retour false.
pred(0) n'est pas défini : limite métier connue, non corrigée ici.

7. DÉMO TEMPÉRATURE — MODÈLE RÉEL
============================================================

27.0 °C devient l'atome t270 (dixièmes), uniquement par encodage.
La politique courante couvre t150..t350, soit 201 valeurs.
Le générateur prépare les équations Anemone : fan(t270)=75, etc.
Leur choix est déclaratif au runtime, pas un if de Java ou du web.

Agent réel dans temperature/regulation.anemone :
sum q in Temperatures: get(temperature(q));tell(temperature_current(q));tell(ventilation(fan(q)))

Pas 1 : choix développé sur Temperatures.
Pas 2 : sélection q=t270 par get, entrée consommée, store vide.
Pas 3 : publication temperature_current(t270).
Pas 4 : résolution fan(t270) et publication ventilation(75).

La mesure affichée reste la dernière entrée appliquée, mémorisée
comme observation ; elle n'est pas présentée comme un terme
temperature encore présent après sa consommation.

Le Java lit fanPower exclusivement dans le terme ventilation :
foncteur ventilation, un argument, lecture de cet argument entier.
Avant publication par le moteur, fanPower est null.
web/js/temperature.js reçoit cette valeur ; fans.js interpole
une vitesse graphique à partir de la PUISSANCE, pas de la température.

Configuration pédagogique actuelle :
<22 °C : 0 % ; 22..<24 : 25 % ; 24..<26 : 50 % ;
26..<28 : 75 % ; 28..35 : 100 %, domaine 15.0..35.0.
Séquence Demo : 20, 23, 25, 27, 30, puis 24 °C.

Modifier config/temperature-policy.json puis lancer :
node experiments/generate-temperature-scenario.mjs
Redémarrer ensuite SmartStock. Le Bridge vérifie les empreintes
de la politique et des définitions pour éviter une incohérence.
Les valeurs ne sont jamais présentées comme une norme médicale.

8. HTTP, SSE ET ENDPOINTS RÉELS
============================================================

HTTP est le mécanisme demande/réponse : un clic envoie une commande,
le serveur répond avec un état ou une erreur.
SSE (Server-Sent Events) est une connexion HTTP ouverte où le serveur
pousse ses snapshots à mesure que le moteur avance.
HTTP sert aux commandes ; SSE permet d'observer les pas intermédiaires.

STOCK, routes historiques conservées :
GET  /api/state
GET  /api/events                       (SSE stock)
POST /api/initialize
POST /api/events/weight
POST /api/events/datamatrix
POST /api/run
POST /api/step
POST /api/reset

Les alias /api/stock/state, /api/stock/events,
/api/stock/initialize, /api/stock/events/weight,
/api/stock/events/datamatrix, /api/stock/run, /api/stock/step,
/api/stock/reset accèdent à cette même session stock.

TEMPÉRATURE :
GET  /api/temperature/state
GET  /api/temperature/events           (SSE température)
POST /api/temperature/initialize
POST /api/temperature/apply?value=27.0
POST /api/temperature/run
POST /api/temperature/step
POST /api/temperature/reset

SYSTÈME :
GET  /api/diagnostics                  (observations réelles, sans mutation)
POST /api/shutdown                     (arrêt de SmartStock uniquement)

Les commandes de démo n'ont pas de corps et demandent
X-SmartStock-Token (obtenu dans GET state) et X-Command-Id unique.
L'arrêt demande uniquement le jeton, sans argument ni commande libre.
Le diagnostic est une lecture locale, pas une commande de moteur.

Le serveur écoute uniquement 127.0.0.1, contrôle Host et Origin et
sert uniquement les ressources autorisées sous web/.
Les archives, sources Java, fichiers arbitraires et le JAR ne sont
pas exposés par une route de téléchargement.

EventHub conserve 128 snapshots, avec des queues/client bornées.
SSE fournit sequence/Last-Event-ID et un heartbeat de 10 s.
Après une perte d'historique, le client reçoit un état récent et
peut signaler un saut de séquence. Le journal n'est pas durable.
AnemoneDataSource relit aussi GET state toutes les 2.5 s.


============================================================
9. LE BLACKBOARD DANS CE PROJET
============================================================

ABBlackboard regroupe le store, les ensembles, équations, procédures
et règles. ABStore est une map mutable de terme structuré vers
une multiplicité entière. Ce n'est pas une liste de simples chaînes.

tell(t) : ajoute une occurrence, retourne true.
  Exemple : tell(poids_change(compresse)).
  Deux tell du même terme donnent une multiplicité 2.

ask(t) : teste sa présence sans consommer, retourne true/false.
  Exemple : bb.ask(retrait_confirme(compresse)) ne l'efface pas.

get(t) : consomme une occurrence si disponible ; sinon false.
  Le moteur ne bloque pas le thread dans l'attente du terme.

nb_occ(t) : multiplicité actuelle, 0 si absent.
  Deux retraits confirmés peuvent donner nb_occ(...)=2.

storeContents : map actuelle des termes/multiplicités.
  Elle est mutable : les sessions la lisent sur leur thread propriétaire
  puis construisent des snapshots détachés pour HTTP/SSE.

La session stock emploie ask et nb_occ pour ses indicateurs actuels
et son compteur ; les deux sessions parcourent storeContents.
La température utilise aussi getall pour retirer l'ancienne télémétrie
avant une nouvelle entrée, sans calculer la nouvelle décision.

Ne pas confondre :
  Blackboard actuel = ce qui reste présent MAINTENANT.
  Observations = capteurs reçus/décision observée pendant l'exécution.
  Journal = suite bornée des observations reçues par le frontend.


============================================================
10. AGENTS ANEMONE INSTRUCTION PAR INSTRUCTION
============================================================

STOCK :
get(poids_change(compresse));
get(datamatrix_detecte(compresse));
tell(retrait_confirme(compresse));
sum q in Stock:
    get(stock(compresse,q));
    tell(stock(compresse,pred(q)))

1. Consommer le poids.
2. Consommer le Data Matrix.
3. Publier la confirmation.
4. Construire un choix d'instances de q.
5. Retenir une branche dont le stock correspondant est disponible.
6. Publier le terme simplifié par les équations pred.

TEMPÉRATURE :
sum q in Temperatures:
    get(temperature(q));
    tell(temperature_current(q));
    tell(ventilation(fan(q)))

1. Construire les branches du domaine discret.
2. Sélectionner et consommer la mesure présente.
3. Publier la mesure traitée.
4. Résoudre fan(q) et publier la puissance.

AnimBachSimulParser.parse_agent analyse la syntaxe en AST.
ABSimulExec reçoit cet AST, le bon Blackboard et un ABSetOfScenes vide.
Chaque run_one retourne un tuple (succès, agent restant).
Le Bridge utilise EXACTEMENT la continuation retournée ; il ne
réécrit pas l'AST pour obtenir un résultat particulier.


============================================================
11. MODE ANEMONE ET MODE DEMO
============================================================

MODE ANEMONE — MOTEUR RÉEL
AnemoneDataSource appelle le serveur local et n'applique pas de règle
de retrait ou de puissance. En panne : message visible, pas de repli
silencieux. Un dernier état visible peut être une observation ancienne,
pas une nouvelle donnée confirmée après déconnexion.

MODE DEMO — DONNÉES SIMULÉES
DemoDataSource et TemperatureDemoDataSource calculent leurs résultats
localement pour montrer les animations sans Bridge. Elles ne prouvent
PAS l'utilisation du moteur Anemone. Leur bandeau reste explicite.

L'ouverture directe de web/index.html en file: sélectionne Demo.
Le mode réel et le diagnostic demandent l'URL HTTP du serveur.
Le diagnostic ne dispose pas d'un faux mode Demo : il interroge
toujours le Bridge, indépendamment du mode choisi auparavant.

13. COMMENT DEBUGGER ET LIRE LA PREUVE
============================================================

LOGS JAVA
La console Run/Debug IntelliJ ou le terminal PowerShell donne les
erreurs de démarrage/compilation et l'URL locale. Les erreurs moteur
capturées pendant un pas apparaissent dans le snapshot/message,
executionStatus=error. Il n'existe pas de fichier log métier automatique.

ÉTAT HTTP
Ouvrir /api/state ou /api/temperature/state ; lire source, sessionId,
sequence, executionStatus, executionStep, remainingAgent et blackboard.
stock et fanPower viennent des vrais termes, pas d'une valeur attendue.

DIAGNOSTIC MOTEUR
Sidebar > SYSTÈME > Diagnostic moteur, ou GET /api/diagnostics.
Le serveur relève System.getProperty(java.version), le mode headless
effectif, le CodeSource et la ressource .class des classes chargées.
Le chemin bridge.properties est affiché dans CONFIGURATION,
séparé de l'origine effective déterminée par le classloader.

Chaque session est échantillonnée sur son thread propriétaire :
classes des objets parser/bb/engine ; identité du Blackboard ;
ensemble et équations lus réellement ; snapshot du store ;
dernière opération instrumentée ; compteur de run_one ;
dernier AST avant/après, booléen de retour et session correspondante.

Les compteurs incluent les appels retournant false. Ils persistent
après RESET dans la même JVM, mais repartent à zéro au redémarrage.
Ils comptent les appels externes du Bridge à run_one, pas les
appels récursifs internes de cette méthode ni le nombre de primitives.
Le dernier run_one peut appartenir à une session précédente après
RESET : comparer son sessionId à celui du Blackboard courant.
Le moteur instancié est null avant le premier prepare, pas inventé.
Les identités hash sont des repères JVM, pas des identifiants durables.
La dernière opération est une observation instrumentée du Bridge,
pas un traçage exhaustif de chaque opération interne de la bibliothèque.

Lire le diagnostic ne fait pas avancer l'agent et ne modifie pas
sequence, le Blackboard ou les compteurs. Les deux sessions sont
échantillonnées successivement, pas dans une transaction globale.
Les noms de classes seuls ne constituent pas une preuve suffisante :
les confronter au JAR observé et aux AST/résultats d'exécution.

NAVIGATEUR
F12 > Console : erreurs JS ; Network : requêtes HTTP, erreurs 4xx/5xx
et flux /api/events ou /api/temperature/events.
Si SSE échoue, l'état peut encore être relu par HTTP ; le journal
peut manquer des étapes. Une séquence sautée est signalée.

BRIDGE ARRÊTÉ / INDISPONIBILITÉ
Une connexion HTTP refusée signifie que le service ne répond pas.
Le diagnostic ne peut pas distinguer un serveur arrêté d'un problème
de transport sans autre preuve : il ne prétend pas connaître la cause.
Une erreur de chargement du JAR empêche le démarrage : voir console.
Le mode Demo n'est jamais activé automatiquement pour masquer cela.

POINTS D'ARRÊT CONSEILLÉS DANS INTELLIJ (à placer manuellement)
LocalServer.handle ; AnemoneSession.input/advance ;
TemperatureEngineSession.command/advance ; publish des deux sessions.
Examiner ast, result, bb et listEqns ; ne pas éditer ces valeurs
pour fabriquer la décision que l'on souhaite montrer.

14. PROUVER ANEMONE AU PROFESSEUR EN QUELQUES CLICS
============================================================

1. Démarrer via la configuration IntelliJ ; ouvrir l'URL locale.
2. Diagnostic moteur : montrer Java/headless, origine JAR,
   classes parser/bb/moteur, 40 équations stock et 201 température.
3. Ouvrir la Démo 01 en ANEMONE, RESET, publier POIDS et DATA MATRIX.
4. Cliquer cinq fois PAS À PAS : l'AST doit contenir
   tell(stock(compresse,pred(40))), le stock 40 a été consommé.
5. Ouvrir Diagnostic : montrer compteur, dernier AST et store réel.
6. Revenir Démo 01, un PAS À PAS : stock 39 apparaît.
7. Diagnostic : dernier AST AVANT contient pred(40), succès true,
   agent terminé ; Blackboard stock contient stock(compresse,39).
8. Démo 02 : appliquer 27.0 °C puis trois PAS À PAS.
9. Montrer tell(ventilation(fan(t270))), puis le quatrième pas :
   ventilation(75). Diagnostic montre la trace correspondante.
10. Expliquer que Demo est une simulation séparée ; ce n'est pas
    le mode utilisé pour cette preuve. Quitter proprement si souhaité.

Les lectures Diagnostic ne réinitialisent aucune session et ne
consomment aucun terme : on peut alterner les vues pendant ces pas.


============================================================
15. GLOSSAIRE ET REPRISE PRATIQUE
============================================================

Bridge : couche Java de transport et d'orchestration entre web et moteur.
JVM : processus qui exécute Java et les classes Scala compilées Anemone.
API : ensemble d'opérations autorisées exposées par le serveur.
HTTP : protocole requête/réponse utilisé pour les commandes et états.
SSE : flux HTTP serveur -> navigateur pour les observations successives.
AST : arbre syntaxique d'un agent, produit par le parseur et exécuté
      par le moteur ; l'AST restant représente la continuation.
Blackboard : environnement partagé des termes et définitions Anemone.
tell : ajouter une occurrence de terme.
get : consommer une occurrence disponible.
ask : vérifier la présence sans consommer.
nb_occ : lire le nombre d'occurrences d'un terme.
Anemone : moteur Scala/JVM réellement utilisé ici pour exécuter les agents.
Data Matrix : code bidimensionnel d'identification ; l'interface contient
      un motif illustratif et un événement simulé de lecture.
Headless : fonctionnement sans fenêtre Swing/graphique du moteur.
Snapshot : copie d'état destinée à l'observation, pas le store mutable.
CodeSource : origine du code d'une classe constatée par la JVM.

POUR REPRENDRE DANS SIX MOIS
Lire notes/DOCUMENTATION-INDEX.txt, puis ce guide.
Lancer le Bridge ; ouvrir Diagnostic ; vérifier le JAR effectivement
chargé. Rejouer les tests avant de modifier les agents.

Commandes de tests (serveur temporaire sur 8092) :
    $env:SMARTSTOCK_URL='http://127.0.0.1:8092'
    node experiments/diagnostics-tests.mjs
    node experiments/api-tests.mjs
    node experiments/data-source-tests.mjs
    node experiments/temperature-api-tests.mjs
    node experiments/temperature-demo-tests.mjs
    node experiments/documentation-tests.mjs
    node experiments/ui-contract-tests.mjs

Faire ui-contract-tests EN DERNIER : son test de Quitter arrête le serveur.
Les diagnostics-tests remettent les stores à leurs valeurs initiales
à la fin ; leur compteur reste cumulatif dans le processus.
Les tests DOM ne remplacent pas la vérification graphique sur le PC.
Ne pas revendiquer de persistance disque : elle n'existe pas ici.

Tutoriels autonomes :
    anemone-scenarios/smartstock-procedure-datamatrix.txt
    anemone-scenarios/smartstock-procedure-temperature.txt
Schémas rapides : les deux fichiers smartstock-schema-*.txt correspondants.
